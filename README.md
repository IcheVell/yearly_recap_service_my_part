# Avito Yearly Recaps — backend contribution

Персональный репозиторий с моей частью командного хакатонного проекта **Avito Yearly Recaps**.

Проект формирует персональные итоги года на основе активности пользователя на Avito: покупок, продаж, просмотров, поисков, избранного, диалогов, отзывов и пользовательских сессий. На основе этих данных сервис собирает статистику, определяет достижения пользователя и участвует в формировании итогового recap.

> Этот репозиторий не является полным зеркалом командного проекта. Здесь собраны код, схема базы данных, миграции и документация, относящиеся к моей зоне ответственности. Некоторые части исходного приложения были реализованы или позднее доработаны другими участниками команды.

**Демо командного проекта:** [http://176.109.107.141](http://176.109.107.141)

## Контекст проекта

За год пользователь совершает на площадке множество действий, но обычно не воспринимает их как единую историю. Идея проекта — использовать уже существующие продуктовые данные и превратить их в персональный сценарий «итогов года».

Backend агрегирует активность пользователя, формирует годовые метрики, работает с накопительной статистикой и системой достижений. Итоговый recap может включать роль пользователя, значимые метрики, достижения и следующее рекомендуемое действие.

## Накопительная статистика пользователя

Для системы глобальных достижений была введена отдельная сущность `UserStats`.

Она хранит статистику, которая не привязана к одному recap-году:

```text
buys_count
sells_count
favorites_count
conversations_count
spent_amount
rating_sum
reviews_count
max_streak_days
max_inactive_gap_days
```

Годовые метрики recap и глобальная статистика достижений разделены: recap анализирует конкретный год, а `UserStats` может учитывать активность пользователя за всё время.

### Инкрементальное обновление

Чтобы не пересчитывать всю историю пользователя при каждой проверке достижений, используется поле:

```text
processed_at
```

`UserStatsRepository` обрабатывает только новые события в интервале:

```text
(processed_at, now]
```

Для накопительных метрик новые значения добавляются к уже сохранённым. Обновление нескольких метрик и перенос `processed_at` выполняются внутри одной транзакции.

В статистику входят, в частности:

- количество завершённых покупок;
- количество завершённых продаж;
- количество добавлений в избранное;
- количество диалогов;
- сумма завершённых покупок;
- сумма рейтингов и количество отзывов;
- максимальная серия активных дней;
- максимальный период неактивности.

## Система достижений

Значительная часть моей работы была связана с проектированием и реализацией системы достижений.

### Декларативные правила

Правила получения достижений не захардкожены по одному в Go-коде. Они хранятся в PostgreSQL в таблице `achievement_rules` в формате `JSONB`.

Простое правило:

```json
{
  "type": "condition",
  "metric": "max_streak_days",
  "operator": ">=",
  "value": 7
}
```

Составное правило:

```json
{
  "type": "all",
  "conditions": [
    {
      "type": "condition",
      "metric": "buys_count",
      "operator": ">=",
      "value": 1
    },
    {
      "type": "condition",
      "metric": "sells_count",
      "operator": ">=",
      "value": 1
    }
  ]
}
```

Поддерживаются типы правил:

```text
condition
all
any
```

и операторы сравнения:

```text
>=
>
<=
<
==
```

Благодаря рекурсивной структуре `RuleNode` правила могут состоять из нескольких условий.

### Rule evaluator

Evaluator сопоставляет метрики из правила с `UserStats` и рекурсивно вычисляет составные условия.

```text
achievement_rules
       ↓
   RuleNode
       ↓
 EvaluateRule
       ↓
 UserStats
       ↓
   true / false
```

Код правил находится в:

```text
backend/internal/engine/rules/
```

### AchievementService

`AchievementService` связывает накопительную статистику и rule engine.

Общий сценарий:

```text
Пользователь
     ↓
Текущий UserStats
     ↓
Синхронизация новых событий
     ↓
Обновлённый UserStats
     ↓
Загрузка achievement_rules
     ↓
EvaluateRule для каждого достижения
     ↓
Выдача выполненных достижений
```

Выдача достижения сделана идемпотентной: повторная проверка правила не создаёт дубликаты в `user_achievements`.

## Recap

Я реализовал начальную версию `RecapService` и части, связанные с хранением recap.

`RecapRepository` сохраняет сформированный результат в PostgreSQL. Payload recap хранится в `JSONB`, а пара `(user_id, year)` используется для работы с итогами конкретного пользователя за конкретный год.

В моей зоне работы также были:

- получение recap пользователя;
- создание и обновление сохранённого recap;
- получение годовой статистики;
- часть интеграции между service- и repository-слоями.

## PostgreSQL

Подключение к PostgreSQL выполняется через GORM.

Конфигурация собирается из переменных окружения:

```dotenv
DB_HOST=db
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=yearly_recaps
DB_SSLMODE=disable
RECAP_YEAR=2026
```

При подключении выполняется `PingContext`, чтобы ошибка соединения обнаруживалась на старте приложения.
